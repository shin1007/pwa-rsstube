# 踏んだ罠 — 画面と操作

components/ · globals.css · 読み進める導線 を触るときに読む。索引は `CLAUDE.md` にある。

**ここに書くのは「決まったこと」ではなく「実際に壊れた話」だけ。**
同じ壊れ方をもう一度させないための記録なので、直し方だけでなく
「どう見えたか（何が起きているように見えたか）」を残すこと。

- **文字の大きさは目盛り（`@theme`）で動かす。クラスを書き替えない。** 「全体的に
  2段階大きく」で `text-xs`（165か所）と `text-sm`（91か所）を1つずつ直すと、必ず
  塗り残しが出る。`--text-xs` などを再定義すれば既存のクラスのまま全部が上がる。
  **`body` にも実寸を入れること**——rem は `:root` 基準なので、クラスを付けていない
  文字だけ 16px で取り残される。**そして実寸を直書きした箇所を探し直すこと。**
  スマホの入力欄には iOS の自動ズーム避けで `font-size: 16px` が入っていて、
  目盛りだけ上げると **text-base（20px）の入力欄がスマホでだけ 16px に縮んだ**
  ——大きくするための変更が、いちばん打ちにくい画面でだけ効かない形になる
  （`max(16px, 1em)` の下限に変えた）。`.prose-rich` の見出しも rem 直書きで、
  放っておくと見出しが本文より小さくなる。**JSX の `text-[15px]` も同じ**——
  記事本文がこれで、一番長く見る文字だけが元の大きさで取り残されていた（23か所あった）。
  **そして大きさを揃えると、今度は見出しと本文の差が消える。** 目盛りを上げたあと、
  `.prose-rich h3` は 1.3rem＝20.8px で本文の 19px と1px しか違わず、`h4` は
  font-size が無くて**本文と完全に同じ**だった（太字と色だけの差）。節の変わり目が
  本文の流れに埋もれて「見出しが無い」ように読まれる。直すときは3つ重ねること——
  大きさ（本文の1.05〜1.65倍）・余白の非対称（上を厚く下を薄く、4:1。見出しは
  下の文の持ち物なので、上下均等だとどちらに属するか読めない）・明るさ
  （本文 zinc-300 に対して見出しは白。太字だけでは目が拾わない）。h2 には罫線も入れる
  ——実際の記事は h2 だけで組まれていることが多く、そこが一番効く。
  **本文の中の見出しは rem ではなく em で書くこと。** rem は :root（16px）基準なので、
  本文の `text-[19px]` を動かしたときに見出しだけが取り残される（この壊れ方を
  一度やっている）。em なら `.prose-rich` の実寸に追随する。
  画面側の小見出し（設定・ダイアログ・一覧の帯）も同じで、`text-sm font-semibold`＝18px は
  まわりの本文 16px と2pxしか違わなかった。14か所に散っているので、クラスを1つずつ
  直さず `.section-title` を1つ置いて当てる。
  そして**入るはずだったものが入らなくなる。** 記事の上の帯は6つのボタンで1行ぎりぎりで、
  溢れた瞬間に flex が縮めにきて **`音声にする` が1文字ずつ縦に折り返り、帯が画面の
  1/4を占めた**。日本語のラベルは1文字でも折り返せるので、横スクロールにもならずに
  黙って縦に伸びる。**並ぶボタンには `whitespace-nowrap` と `shrink-0` を付け、
  狭い画面用の短い形を持たせること**（読み上げには `aria-label` で長いほうを渡す）。

- **`.prose-rich` の間隔を「直下の子」で書かないこと。** `> * + *` で段落の間隔を
  付けていたが、**一度も当たっていなかった**。抽出した本文は
  `<div><div><p>…</p><p>…</p></div></div>` のように包まれていて、直下の子は div 
  ひとつだけ。実データ10本で当たった要素は全部で0個、段落は13〜111個あった。
  Tailwind の preflight が `<p>` の既定マージンも消すので、**段落の間隔はゼロ**の
  まま行間1.9だけで文が続き、改行と段落の切れ目が見分けられなかった。
  深さを問わず要素名で当てること。**下マージンだけにする**——上マージンだと
  先頭の段落のぶんが包みの div をすり抜けて本文の上に隙間を作る（マージンの相殺）。
  1字下げ（`text-indent`）は入れない。日本語では字下げと段落間の空きはどちらか
  片方にするもので、スクロールして読む画面なら空きのほうが切れ目を見つけやすい。

- **「前の記事／次の記事」の帯は、位置が出せないと丸ごと消える。** 出すかどうかは
  `prevHref || nextHref` で決めていて、**一覧に居ない記事は位置が出せない**。
  未読ビューでこれが常に起きていた——記事を開くと既読になり、同じ描画で引いた
  一覧からはもう抜けているため（`index === -1`）。PCは一覧が横に見えているので
  気づきにくいが、**スマホには一覧へ戻る以外の導線が無い**ので、1本目を開いた
  瞬間から読み進める手が無くなる。
  以前は「未読ビューでは引いても空振りだから」と、位置の引き直しごと飛ばしていた。
  空振りなのは事実だが、**空振りしたときに何を出すかを決めていなかった**のが穴。
  いまは id で見つからなければ `published_at` で「居たはずの場所」を出す
  （`app/page.tsx`）。並びが新着順だけになった（`0037`）ので、この手はいつでも使える。

- **「次の記事」は一覧の1ページ目しか見ていなかった（60件目で止まる）。** 前後の
  行き先はサーバーの `articles`（当時 `PAGE_SIZE = 60`。いまは30）から数えていたので、末尾を開くと
  `index === articles.length - 1` で「次は無い」になる。一覧を下までスクロールすれば
  61件目以降は継ぎ足されるのに、**読み進めるほうだけが60でぴたりと止まる**。
  実測（ブラウザで → を66回）で、必ず60件目で止まることを確認した。
  ちょうど1ページぶんで終わっている一覧は「終わり」と「続きがある」の区別が付かないので、
  そのときだけ id しか運ばない一覧を引き直す（`app/page.tsx` の `atPageEnd`）。
  **端でだけ引き直すこと**——毎回引くと、読み進める全ページに1往復増える。

- **未読ビューでは「前の記事」に戻れない。来た道はブラウザしか知らない。**
  前後はサーバーが一覧から出すが、未読ビューでは開いた記事がその場で既読になって
  一覧から抜ける。つまり**さっき読んだ記事は、次の描画の一覧に1件も残っていない**。
  その状態で「前」を出すと、日付の近い**別の未読**が出てくる。実測では → を12回
  押してから ← を押すと、来た道ではない記事へ飛び、3回目で行き先が尽きて止まった。
  サーバー側では直せない（「いま読んだばかり」を一覧に残すのは未読の定義を変えること
  になるし、どこまでを「さっき」とするかも決められない）。開いた順を覚えているのは
  ブラウザだけなので、`lib/trail.ts` にその場かぎりの並びとして持つ。
  **来た道があるのは「戻る」側だけ**——進む側はいつもどおり一覧の続きを使う。
  **見に行く場所を3つに分けないこと。** ← → キー（`ArticleList`）・スワイプ
  （`ArticleSwipe`）・画面下のボタン（`ArticleNav`）は同じ `useNeighbours()` を通す。
  下のボタンを client に切り出したのはこのため。行き先が食い違うと、指とキーで
  違う記事に着く。

- **押し続けると一歩も進まない（← → が「途中で止まる」の正体）。** 前後の行き先は
  サーバーが描き直すまで変わらないので、着く前にもう一度押すと**いま向かっている先へ
  もう一度**押したことになる。同じ場所への `router.push` は React の遷移をやり直させる
  だけなので、押し続けているあいだ永久に着かない。**遅いのではなく、進まない。**
  実測（手元・300ms 間隔で40回）: 進んだのは**3件だけ**で、13回続けて何も起きない
  場所があった。キーの自動リピートは30ms 間隔なので、押しっぱなしではまず抜け出せない。
  `useTransition` で移動中を見て、着くまで受けない。そして**押されたぶんは数えて
  覚えておく**——捨てると連打が効かない（同じ実測で20件、最後の1回だけ覚えても28件）。
  数えれば8回押して8つ先に着く（`history.length` で実測。ただの遅れになる）。
  **押しっぱなしの自動リピートだけは数えないこと**（`e.repeat`）。30ms 間隔で
  際限なく届くので、数えると指を離したあとも延々と進み続ける。**連打と押しっぱなしは
  この旗でしか見分けられない**（実測: repeat 付きを40回投げても移動は1回）。
  溜める数には上限を置く。溜まったぶんは1件ずつ本当に開いていく（既読も付く）ので、
  行き過ぎたぶんは手で戻すことになる。
  **確認は「押して動くか」ではなく「連打して何回ぶん進むか」で行うこと。** 1.6秒
  空けて66回押したときは1件も取りこぼしが無く、この壊れ方は見えていなかった。
  進んだ数は URL を拾うより `history.length` の差で見るほうが正確
  （速すぎて途中の URL は拾いきれない）。
- **ホームバーぶんの余白は、ボタンの padding に足すと「押せない空白」に見える。**
  当たり判定を下端まで伸ばすために `padding-bottom: calc(0.5rem + env(safe-area-
  inset-bottom))` をリンクに入れていた。判定は正しく届くのだが、**文字は上に
  寄ったままで、その下に40px近い何も無い帯ができる**。押せないように見えるし、
  iPhone はいちばん下の数十pxをホームバーの操作に使うので、実際そこは反応しない
  こともある。中身を44px（タブは48px）の枠に入れて上下中央に置き、ホームバーぶんは
  その下に土台として残す（iOS のタブバーと同じ組み方）。**帯には色を敷くこと**
  ——透明だとそこだけ本文の背景が覗いて「余った隙間」に見える。
  なお nav 側の padding にするのは論外（どのリンクにも当たらない死んだ帯になる）。

- **指の当たり判定は44px。文字ではなく枠に下限を入れる。** 記号にして詰めた
  記事の操作の帯は、実測で 29〜40 × 32 しかなく、隙間は2pxだった（Apple 44pt /
  Material 48dp / WCAG 2.5.8 は 24×24）。文字を大きくして広げると、記号（スマホ）と
  日本語ラベル（PC）で必要な大きさが違うのでどちらかが不格好になる。`min-width`
  `min-height` なら見た目は変わらず判定だけ広がる。**採寸はブラウザにさせること**
  ——`getBoundingClientRect()` を全ボタンに回せば一覧で出る。ただし擬似要素で
  広げた判定はそれに映らないので、そこは `elementFromPoint` で確かめる。

- **「まだ何も無い」状態を、実在する値と同じにしないこと。** 来た道を覚える
  `lib/trail.ts` の初期値が `{ key: '', ids: [], pos: -1 }` で、**絞り込みが何も
  無い一覧（＝未読ビューをそのまま開いた状態）のキーも空文字**だった。キーが
  一致してしまうので作り直しの分岐に入らず、その先の `at === state.pos` が
  `-1 === -1` で真になって**1件も記録されない**。フォルダや検索から開いたときは
  キーが空でないので正しく動く——だから「未読のときだけ前に戻れない」という、
  再現条件が分かりにくい形で出た。初期状態は `null` のように、実在しない値にする。

- **運ぶ列を減らすときは、画面に出ていない使い道を探すこと。** 一覧の payload から
  `url` を落としたら、キーボードの `v`（元記事を新しいタブで開く）が
  `window.open(undefined)` になって **about:blank が開く**ようになった。
  `window.open` は `string | undefined` を受けるので型検査では気づけないし、
  行のどこにも出ていない列なので画面を見ても分からない。JSX を grep するだけでは
  足りない——ショートカット・スワイプ・共有のように、**描画しないで値を使う場所**
  を先に見る。

- **押しても何も起きない時間には、帯を1本出す。** 画面遷移は 250〜380ms かかるが、
  そのあいだ画面は**押す前のまま**になる——React の遷移は新しい中身が揃うまで
  今の画面を出したままにするので、これは正しい動きなのだが、**押せたのかどうかが
  分からない**。ボタン（スター・あとで・書き出し）は押した瞬間に見た目が変わるので、
  遷移だけが無反応に見えていた。
  - **骨組みに差し替えないこと。** `loading.tsx` を置くと押すたびに一覧が消える。
    いま読んでいるものを消すのは、待たせるより悪い。出すのは上端の細い帯だけ
    （`components/NavProgress.tsx`）。
  - **進み具合は出さない。** 本当のところは分からないので、出せば嘘になる。
    往復するだけの動きにしてある。
  - リンク（サイドバー・下部タブ）は `useLinkStatus`、こちらから `router.push` する
    ところ（一覧の検索・ビュー切り替え・記事を開く）は `useTransition` の pending。
    **先読みが間に合ったリンクでは pending にならない**ので、速いときは何も出ない
    ——それが正しい。

- **設定の「いちばん下」は `Diagnostics` の中ではない。** 起動の内訳を
  「設定のいちばん下に出しました」と伝えたのに、実際は**真ん中**に出ていた。
  `Diagnostics`（取り込みの進み具合・AI の使用量）は `<Suspense>` で
  **先に流している**節で、コードの見た目は後ろでも**画面では上のほう**にある。
  本体の最後に置きたいなら、フィード一覧の `</section>` の直後、
  `</main>` の手前に書くこと。**「どこを見てください」と書く前に、
  実際に見出しの並びを取って確かめる**こと
  （`[...document.querySelectorAll('h2')].map((h) => h.textContent)`）。

- **記事を移っても、client 部品の state は付いてくる。** スターを付けてから
  「次の記事」へ進むと、**次の記事にも★が付いて見えた**。`ArticleActions` の
  楽観値（`shown`）は記事ごとの状態なのに、部品は同じ route の中の遷移では
  unmount されないので、押したときの値がそのまま次の記事に残る。
  サーバー値に合わせる仕掛けは入っていたが、見ていたのが `active` の**変化**
  だけだった——「スター無し → 押して付けた → 次の記事もスター無し」では
  `active` は false のまま動かないので差が出ず、合わせ直しが一度も走らない。
  - **合わせる条件には、どの行の値かを入れること**（`articleId` と `active` の組）。
    「サーバー値が変わったら」ではなく「別の記事になったら」でも戻す。
  - **合わせるのは render の中で**（`useState` に前回の組を持って比べる）。
    `useEffect` だと描いたあとに走るので、切り替えた直後の1フレームだけ
    前の記事の★が見える。
  - 同じ理由で、押した結果の帯（`ActionFlash`）も記事が変わったら消す。
    残った「取り消す」は**前の記事**を戻しながら、いま見ている記事の★を
    書き替える（closure が押したときの id を握っているため）。

- **同じ罠は「記事ごとの state を持つ部品」全部にある。** スターと同じ形の
  持ち越しが、記事画面の他の部品にも残っていた。いちばん困るのは**音声**で、
  `MediaButton` は押すとボタン自体が「受け付けました／開く」のリンクに
  置き換わるため、次の記事へ移ると**「音声にする」が押せないまま**になる
  （リンク先も前の記事の音声）。他に、書き出しの失敗文（`ExportButton`）、
  スマホのメニューの開閉と知らせと「開く」（`ArticleMobileMenu`）、
  「前回の続きから開きました」（`ReadingPosition`）。
  - **記事ごとの state を持つ部品には `key={a.id}` を付ける**（ArticleView）。
    中で id を突き合わせる手もあるが（`ArticleNav` の notice はそうしている）、
    状態が2つ以上あるなら key のほうが数え落としが無い。
  - 見分けかたは「この state は記事の属性か」。属性なら記事が変われば捨てる。
  - 同じ形は `/watch/:id` にもある（`usePlayer` はどのクリップまで聴いたかを
    持つ）。アプリ内に watch→watch の導線は無いので出なかったが、`key` を付けた。
    下部プレイヤーの `DockPlayer` は最初から key が付いている。

- **「新しい記事が3件」と出たのに、一覧は1件も増えなかった。** もう一度押すと
  「新着はありません」。電波の悪いところで踏んだが、電波とは関係が無い。
  更新の文面が巡回の `newArticles` をそのまま出していて、これは一覧と2点で食い違う:
  - **新着は要約が付くまで一覧に出ない**（0047。鍵を入れている人・取り込んで24時間以内）。
    取り込んだ直後は必ず要約待ちなので、押した直後の一覧には絶対に出ない。
    2回目はもう取り込み済みなので「新着なし」になり、「来たはずの記事が消えた」に見える。
  - **巡回は全員の購読を回す**（`feeds_to_poll`）。件数には他人のフィードの新着も入る。
  - 直し: 文面は自分のクライアント（RLS で自分の記事・自分の言語の要約だけ）で数え直し、
    要約待ちで出ていない件数を言う（`lib/feeds/refresh-message.ts`）。**画面に出す数は、
    同じ画面で数えて確かめられる数にすること。** 裏の処理の件数は、見える件数ではない。
